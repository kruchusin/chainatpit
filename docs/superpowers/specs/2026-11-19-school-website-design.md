# เอกสารออกแบบ: เว็บไซต์โรงเรียน (Cloudflare + Firebase)

วันที่: 2026-11-19
สถานะ: ร่าง รอผู้ใช้อนุมัติ

---

## 1. เจตนาและเหตุผล

โรงเรียนต้องการเว็บไซต์ที่
- **ผู้ปกครองและบุคคลทั่วไป** เข้ามาอ่านข่าวสารและประชาสัมพันธ์ได้โดยไม่ต้องล็อกอิน
- **ครูและบุคลากร** ล็อกอินเพื่อดูแลเนื้อหาเองได้ตามสิทธิ์ โดยสิทธิ์แบ่งตาม **กลุ่มสาระการเรียนรู้** และ **ฝ่ายงาน**

ไฟล์เว็บวางบน **Cloudflare** และเก็บข้อมูลใน **Firebase** เว็บนี้จะมาแทนเว็บเดิมของโรงเรียนชัยนาทพิทยาคม (www.chainatpit.ac.th) ซึ่งตอนนี้ทำด้วย Google Sites ระบบใหม่จะแบ่งสิทธิ์การดูแลเนื้อหาตามฝ่ายและตัวบุคคล โฟลเดอร์ของโปรเจกต์ (`C:\xampp\htdocs\computer`) ยังว่างอยู่ จึงเริ่มใหม่ทั้งหมด ไม่ใช้ PHP หรือ MySQL ของ XAMPP

## 2. เป้าหมาย / สิ่งที่ไม่ทำ / สิ่งที่ถือว่าล้มเหลว

**เป้าหมาย**
- หน้าบ้านแสดงข่าว ประกาศ ข้อมูลบุคลากร และหน้าของแต่ละกลุ่มสาระและฝ่ายงาน
- หลังบ้านให้แต่ละคนจัดการข้อมูลได้ตามบทบาท (ดูหัวข้อ 4)
- ครูทุกคนมีบัญชีของตัวเองและแก้ข้อมูลส่วนตัวได้
- สิทธิ์ต้องบังคับใช้จริงที่ฐานข้อมูล (Firestore Security Rules) ไม่ใช่แค่ซ่อนปุ่มในหน้าเว็บ

**สิ่งที่ไม่ทำในรอบนี้**
- ไม่มีบัญชีนักเรียนหรือผู้ปกครอง
- ไม่มีระบบเกรด ส่งงาน หรือตารางเรียนออนไลน์
- ไม่มีขั้นตอนอนุมัติข่าวก่อนเผยแพร่ (บันทึกแล้วเผยแพร่ทันที แต่ออกแบบให้เพิ่มทีหลังได้)

**ถือว่าล้มเหลว แม้ระบบจะทำงานได้**
- ผู้ประชาสัมพันธ์ประจำฝ่ายแก้ข้อมูลของฝ่ายอื่นได้ หรือครูแก้ข้อมูลของครูคนอื่นได้ เมื่อเรียก Firestore ตรงโดยข้ามหน้าเว็บ
- ครูที่ไม่ได้เขียนเว็บเป็นหลักดูแลต่อไม่ได้ เพราะต้องมีเครื่องมือหรือขั้นตอน build ที่ซับซ้อน
- เกิดค่าใช้จ่ายรายเดือนสำหรับโรงเรียนขนาดปกติ

## 3. ข้อจำกัด

- **โฮสต์:** Cloudflare Pages (ไฟล์ static + Pages Functions)
- **ข้อมูล:** Firebase Authentication (อีเมลและรหัสผ่าน) และ Cloud Firestore ในโปรเจกต์ Firebase `chainatpit-a8c9c` (location `asia-southeast1`) โปรเจกต์นี้มี Realtime Database อยู่ด้วย แต่เว็บนี้ **ไม่ใช้** (ผู้ใช้ยืนยันว่าใช้ Firestore)
- **ไม่มีขั้นตอน build:** ใช้ HTML, CSS และ JavaScript ธรรมดา (ES modules) และโหลด Firebase JS SDK v10+ จาก CDN (gstatic)
- **ภาษา:** หน้าเว็บเป็นภาษาไทย ฟอนต์ Sarabun หรือ Prompt จาก Google Fonts
- **ต้องรองรับมือถือ:** ผู้ปกครองส่วนใหญ่เปิดจากมือถือ และมักเปิดผ่านลิงก์ที่แชร์ใน Facebook หรือ LINE
- **ข้อเท็จจริงที่ตรวจแล้ว (พ.ย. 2026)**
  - การลากวางไฟล์ (Direct Upload) ใน Cloudflare Dashboard **ไม่รองรับโฟลเดอร์ `/functions`** ถ้าจะใช้ Pages Functions ต้อง deploy ผ่าน Wrangler CLI หรือเชื่อม GitHub (ดูหัวข้อ 9 ข้อ 1)
  - Cloud Storage for Firebase **ต้องใช้แผน Blaze** (ต้องผูกบัตร) ตั้งแต่ 3 ก.พ. 2026 แต่ยังมีโควตาใช้ฟรีอยู่ (ดูหัวข้อ 9 ข้อ 2)
- **ห้ามกระทบเว็บเดิม:** www.chainatpit.ac.th (Google Sites) ต้องใช้งานได้ตามปกติจนถึงวันเปลี่ยน DNS

## 4. บทบาทและสิทธิ์ (ผู้ใช้กำหนดเอง)

| บทบาท | สิทธิ์ |
|---|---|
| `admin` ผู้ดูแลระบบ | ทำได้ทุกอย่าง: จัดการบัญชีผู้ใช้ กำหนดบทบาท สร้างหรือลบกลุ่มสาระและฝ่ายงาน ตั้งค่าเว็บ |
| `pr_central` ฝ่ายประชาสัมพันธ์ส่วนกลาง | สร้าง แก้ไข และลบข่าวของ **ทุก** ฝ่ายและกลุ่มสาระ |
| ผู้ประชาสัมพันธ์ประจำฝ่าย (`prDepartments` ไม่ว่าง) | จัดการข่าว ข้อมูลบุคลากร และหน้าของ **ฝ่ายหรือกลุ่มสาระที่ตัวเองรับผิดชอบเท่านั้น** |
| `teacher` ครูทุกคน | แก้ไขข้อมูลส่วนตัวของตัวเอง |

**ข้อเสนอของฉัน (ผู้ใช้ยังไม่ได้ยืนยันโดยตรง)**
- หนึ่งบัญชีเป็นผู้ประชาสัมพันธ์ได้หลายฝ่าย โดยใช้ `prDepartments` เป็น array
- บทบาทเก็บใน Firestore ที่ `users/{uid}` และให้ Security Rules อ่านด้วย `get()` ไม่ใช้ custom claims เพราะแอดมินจะเปลี่ยนสิทธิ์จากหน้าเว็บได้ทันทีโดยไม่ต้องมีโค้ดฝั่งเซิร์ฟเวอร์
- ฟิลด์ที่ครูแก้เองได้: รูป ประวัติ วุฒิการศึกษา และอีเมลที่ใช้ติดต่องาน ส่วน **ตำแหน่ง** และ **สังกัด** ให้ผู้ประชาสัมพันธ์ของฝ่ายหรือแอดมินเป็นผู้แก้ เพื่อไม่ให้ครูย้ายตัวเองไปอยู่ฝ่ายอื่น
- ผู้ประชาสัมพันธ์ประจำฝ่ายแก้ข้อมูลบุคลากรที่สังกัดฝ่ายตนได้ทุกฟิลด์ ยกเว้นสังกัดของฝ่ายอื่น คือเพิ่มหรือลบได้เฉพาะ deptId ที่อยู่ใน `prDepartments` ของตน ถ้าครูอยู่หลายฝ่าย ผู้ประชาสัมพันธ์ของทุกฝ่ายนั้นแก้ได้ (คนที่แก้หลังสุดเป็นผล)
- การสร้างหรือลบข้อมูลบุคลากรทำได้เฉพาะแอดมิน เพราะต้องทำพร้อมกับการสร้างบัญชี ผู้ประชาสัมพันธ์ประจำฝ่ายตั้ง `active=false` เพื่อซ่อนบุคลากรจากหน้าบ้านได้
- **ข้อมูลส่วนบุคคล (PDPA):** หน้าบ้านไม่แสดงเบอร์โทรส่วนตัว ข้อมูล staff ที่เป็นสาธารณะมีเฉพาะชื่อ ตำแหน่ง รูป ประวัติ วุฒิ และอีเมลงาน (ถ้าเจ้าตัวกรอก) โดยไม่เก็บเบอร์โทรในระบบ
- **การเข้าสู่ระบบ:** ใช้อีเมลและรหัสผ่าน Function ของแอดมินตั้งรหัสผ่านเริ่มต้นและรีเซ็ตรหัสให้ได้ จึงใช้งานได้แม้ครูบางคนไม่ได้เช็กอีเมล ส่วนปุ่ม "ลืมรหัสผ่าน" เป็นทางเลือกเพิ่มเติม

## 5. แนวทางที่พิจารณา

1. **HTML/CSS/JS ล้วน + Firebase โดยตรง + Cloudflare Pages Functions เฉพาะงานที่ต้องใช้สิทธิ์เซิร์ฟเวอร์** ← **ผู้ใช้เลือกแนวทางนี้**
   ไม่มีขั้นตอน build ได้ใช้ฟรี คนดูแลต่อที่เป็นครูแก้ไขได้ ข้อเสียคือโค้ดในหน้าหลังบ้านซ้ำกันบ้าง
2. เฟรมเวิร์ก (Vue + Vite) แล้ว build ขึ้น Pages: โครงสร้างโค้ดดีกว่าในระยะยาว แต่ต้องใช้ Node.js และต้อง build ทุกครั้ง ทำให้ดูแลยากสำหรับครูทั่วไป
3. API หลังบ้านเต็มรูปแบบบน Workers: ควบคุมได้มากที่สุด แต่งานมากขึ้นราว 2–3 เท่า และทำซ้ำสิ่งที่ Security Rules ทำได้อยู่แล้ว

**เหตุผลที่ต้องมี Function อย่างน้อยหนึ่งจุด:** Firebase client SDK สร้างบัญชีให้ผู้อื่นไม่ได้ เพราะ `createUserWithEmailAndPassword` จะล็อกอินเป็นผู้ใช้ใหม่ทันที งาน "แอดมินสร้าง ปิด หรือรีเซ็ตบัญชีครู" จึงต้องทำฝั่งเซิร์ฟเวอร์ด้วย service account

## 8. กฎความปลอดภัย (สรุปเจตนา ผู้สร้างเขียนเป็น `firestore.rules`)

- **อ่าน:** ทุกคนอ่าน `departments`, `staff` (เฉพาะ `active`), `news` (เฉพาะ `published`) และ `settings` ได้ ส่วน `users/{uid}` อ่านได้เฉพาะเจ้าของบัญชีและ admin
- **news:**
  - `admin` และ `pr_central` เขียนได้ทุกข่าว
  - ผู้ประชาสัมพันธ์ประจำฝ่ายสร้างหรือแก้ได้เมื่อ `departmentIds` ทั้งก่อนและหลังแก้อยู่ใน `prDepartments` ของตน (`hasOnly`) และต้องไม่ว่าง ข่าวทั่วไปของโรงเรียนจึงเป็นของส่วนกลางเท่านั้น
- **staff:**
  - admin แก้ได้ทุกฟิลด์
  - ผู้ประชาสัมพันธ์ประจำฝ่ายแก้ได้เมื่อบุคลากรคนนั้นสังกัดฝ่ายที่ตนรับผิดชอบ
  - เจ้าตัว (`staff.uid == request.auth.uid`) แก้ได้เฉพาะ `photoUrl`, `bio`, `education` และ `email`
  - ผู้ประชาสัมพันธ์ประจำฝ่ายเปลี่ยน `departmentIds` ได้เฉพาะส่วนที่อยู่ใน `prDepartments` ของตน (ฝ่ายอื่นในรายการต้องคงเดิม) และสร้างหรือลบเอกสารไม่ได้
- **departments:** admin สร้างและลบได้ ผู้ประชาสัมพันธ์ของฝ่ายนั้นแก้ได้เฉพาะ `description` และ `coverUrl`
- **users, settings:** admin เท่านั้น
- ทุกการเขียนต้องมาจากบัญชีที่ `disabled == false`
- ต้องมีชุดทดสอบ Rules ด้วย Firebase Emulator (`@firebase/rules-unit-testing`) ครอบคลุมกรณีในหัวข้อ "ถือว่าล้มเหลว"

## 9. การตัดสินใจเรื่อง deploy, รูปภาพ, โดเมน และการย้ายข้อมูล (ผู้ใช้เลือกแล้ว)

1. **Deploy: เชื่อม GitHub กับ Cloudflare Pages** (ผู้ใช้เลือก)
   - สร้าง repo บน GitHub ผู้ดูแลอัปโหลดหรือแก้ไฟล์ผ่านหน้าเว็บ GitHub แล้ว Cloudflare deploy ให้อัตโนมัติ
   - ตั้งค่า Pages: Build command ว่าง, Build output directory = `public` ส่วน `functions/` อยู่ที่ root ของ repo
   - service account ของ Firebase เก็บเป็น encrypted environment variable ของ Pages ห้าม commit ลง repo
   - `README.md` ต้องมีขั้นตอนทีละขั้นสำหรับครูที่ไม่เคยใช้ GitHub
2. **รูปภาพ: Firebase Storage บนแผน Blaze + ตั้ง budget alert** (ผู้ใช้เลือก)
   - ตั้ง budget alert ที่ระดับต่ำ เช่น 100 บาท/เดือน
   - path: `news/{newsId}/…`, `staff/{staffId}/photo.jpg`, `departments/{deptId}/…`, `site/…`
   - `storage.rules` ใช้ตรรกะสิทธิ์เดียวกับ Firestore (อ่านบทบาทผ่าน `firestore.get()`) อ่านได้ทุกคน จำกัดเขียนเฉพาะรูปภาพไม่เกิน 2 MB หลังย่อฝั่ง client
   - เอกสาร PDF ที่ให้ดาวน์โหลดยังเก็บใน Google Drive ได้ตามเดิม เพราะเป็นลิงก์ให้กดเปิด ไม่ได้ฝังในหน้าเว็บ
3. **โดเมน: www.chainatpit.ac.th** (ใช้อยู่แล้ว ปัจจุบันชี้ไป Google Sites)
   - ทำเว็บใหม่บน `*.pages.dev` ให้เสร็จก่อน แล้วค่อยเปลี่ยน DNS ของ `www` เป็น CNAME ไปที่ Pages ในวันเปิดใช้ ไม่ต้องย้าย nameserver ของโดเมนทั้งหมดมา Cloudflare ส่วนโดเมนเปล่า `chainatpit.ac.th` ให้ redirect ไป www ที่ผู้ให้บริการ DNS เดิม
   - เพิ่มทั้ง `www.chainatpit.ac.th` และ `*.pages.dev` ใน Authorized domains ของ Firebase Auth
   - ต้องหาคนที่มีสิทธิ์แก้ DNS ของโดเมน .ac.th ก่อนวันเปิดใช้ (ผู้ใช้ต้องประสาน)
4. **ย้ายข้อมูลจากเว็บเดิม (Google Sites)** (ผู้ใช้ต้องการย้าย)
   - เว็บเดิมมี: ข้อมูลสถานศึกษา, บุคลากรแยกตามฝ่ายบริหารและกลุ่มสาระ 8 กลุ่ม + แนะแนว/ธุรการ/บุคลากรสนับสนุน, ข่าวปีการศึกษา 2567–2569, ภาพกิจกรรม (โฟลเดอร์ Google Drive), เอกสารดาวน์โหลด (PDF ใน Drive), หน้า ITA และ Google Sites ย่อยของบางกลุ่มสาระหรือโครงการ (Gifted, STEM ฯลฯ)
   - Google Sites ไม่มี API สำหรับ export และข่าวแต่ละเรื่องไม่มี URL ของตัวเอง จึงให้ผู้สร้างเขียน **สคริปต์นำเข้าครั้งเดียว** ที่ดึงหน้า archive รายปีและหน้าบุคลากร แปลงเป็น JSON ให้คนตรวจทาน แล้วนำเข้า Firestore พร้อมคัดลอกรูปขึ้น Storage
   - ข่าวที่สคริปต์แยกไม่ได้ ให้กรอกเองผ่านหลังบ้าน เกณฑ์ที่ยอมรับได้คือย้ายข่าวปี 2569 ครบ ส่วนปีก่อนหน้าย้ายเท่าที่ทำได้
   - ทำ redirect จาก URL ภาษาไทยของหัวข้อหลักในเว็บเดิมไปหน้าใหม่ โดยใช้ไฟล์ `public/_redirects`
   - Google Sites ย่อยของกลุ่มสาระและโครงการ: หน้า department ใหม่มีช่อง "ลิงก์เว็บไซต์ของกลุ่ม" ชี้ไปที่เดิม ไม่ย้ายเนื้อหา

## 9.1 ส่วนที่เพิ่มจากการดูเว็บเดิม (ข้อเสนอของฉัน ผู้ใช้ตัดออกได้)

เว็บเดิมมีเนื้อหา 3 แบบที่ไม่ได้คุยกันไว้ ถ้าไม่มีในเว็บใหม่ การย้ายจะทำให้เนื้อหาหายไป ฉันจึงเพิ่มเข้ามาแบบเรียบง่ายที่สุด
- **ภาพกิจกรรม:** ใช้ข่าวที่มีรูปหลายรูปแทน โดยเพิ่มหน้า `/gallery.html` ที่แสดงข่าวที่มีรูปเป็นตาราง ไม่ต้องสร้าง collection ใหม่ อัลบั้มเก่าใน Drive ให้ใส่เป็นลิงก์ในข่าว
- **เอกสารดาวน์โหลด:** เพิ่ม collection `documents/{id}` {title, url (ลิงก์ Drive), category, departmentId?, year, order} หน้าบ้าน `/documents.html` และหลังบ้าน `/admin/documents.html` ใช้สิทธิ์แบบเดียวกับข่าว
- **หน้า ITA:** ใช้ `documents` ที่ category = "ITA" และแสดงเป็นหน้า `/ita.html` เรียงตามรหัสตัวชี้วัด (O1, O2, …)
- **หน่วยงานที่ไม่ใช่กลุ่มสาระหรือฝ่าย** (แนะแนว, ธุรการ, บุคลากรสนับสนุน, คณะผู้บริหาร): เพิ่ม `type: "unit"` ใน departments เพื่อให้จัดกลุ่มบุคลากรได้แบบเว็บเดิม

## 10. สิ่งที่ปล่อยให้ผู้สร้างตัดสิน

- ตัวแก้ไข rich text (เช่น Quill) และไลบรารีย่อขนาดรูปก่อนอัปโหลด (ฝั่ง client ไม่เกินราว 1600px)
- การแบ่งหน้าข่าว (Firestore cursor, ครั้งละ 12 ข่าว) และ index ที่ต้องใช้
- ดีไซน์และสีของหน้าเว็บ (ควรรับโลโก้และสีของโรงเรียนจากหน้า settings)
- รายละเอียดการตรวจ token ใน Functions และการเก็บ service account key เป็น secret ของ Cloudflare
- ข้อมูลเริ่มต้น (seed) ของกลุ่มสาระ 8 กลุ่ม และฝ่ายงาน 4 ฝ่าย (วิชาการ, บุคคล, งบประมาณ, บริหารทั่วไป) ให้ตรงกับเว็บเดิม แอดมินแก้ไขได้ภายหลัง
- วิธีดึงข้อมูลจากเว็บเดิม (parse HTML ของ Google Sites) และรูปแบบ JSON สำหรับตรวจทาน
- รายการ redirect ใน `_redirects`
